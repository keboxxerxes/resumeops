# ResumeOps SDD workflow

This is the canonical plan and acceptance map for the existing end-to-end SDD cycle. It continues the approved specification without milestones or a restart. Read `SPEC.md`, `AGENTS.md` and `requirements/RESUME_CONTENT.md`; historical plans/reports are superseded only after their evidence has been consolidated and independent cleanup approval recorded.

## Scope and operating environment

Ubuntu CI is canonical for Terraform and complete implementation verification. Native Windows Terraform is **OUT OF SCOPE**; its historical provider mTLS failure was not repaired. Windows remains suitable for browser checks, editing, VS Code and Codex. Preserve Terraform/provider pins, both provider lockfiles and their original integrity entries, dependency locks, TLS/mTLS verification and all mandatory checks. No diagnostic workaround or weaker verification is permitted.

The project remains a small static resume, private S3/CloudFront Terraform and safe workflow source. Only credential-free validation workflows may execute during private verification. AWS/content/drift/rollback/destroy implementations remain inert templates outside `.github/workflows`; active CI must have no AWS credentials, OIDC write permission, remote backend, plan/apply/destroy/deployment path, including indirect script calls. Restoring operational workflows requires separate explicit human authorization and independent review. No public publication, AWS/IAM/resource creation, merge or destruction is authorized. Prepare audited local cleanup first; a subsequent private push requires applicable separate explicit authorization.

## Threat model and mandatory boundaries

- Untrusted PRs/dependencies must never obtain cloud credentials. Active verification is credential-free, pins actions, validates inputs and rejects indirect operational execution; future privileged templates require trusted reviewed main, exact OIDC trust and independently verified protected environments.
- IAM escalation/state theft are constrained by distinct runtime roles, exact resource/key/lock scopes and no runtime IAM/bootstrap administration. First resource creation/recreation needs an authorized local operator's exact privately reviewed saved plan, followed by exact distribution/OAC/header-policy ID binding; wildcard CloudFront tagging/creation is not an acceptable substitute.
- Plan leakage/tampering and approval bypass require private substantive plan review, authenticated ciphertext-only handoff if needed, digest/source/operation/freshness checks and protected approval after review. A digest alone is not substantive review.
- Public origin access/insecure transport are blocked by S3 public blocks, SSE-S3, TLS policies and distribution-scoped OAC; CloudFront uses HTTPS redirects and restrictive headers. Default-certificate legacy viewer TLS behavior remains a documented exception, not a TLS1.2 minimum claim.
- Concurrent operations/destruction require native state locks, repository-wide non-cancelling production concurrency, read-only drift and typed protected site-only destroy. Local operators must coordinate beyond repository concurrency. Bootstrap/state removal needs separate authorization.
- Privacy and evidence loss are addressed by approved content only, secret scans and sanitization, individual exception review and independent inventory approval before any cleanup deletion or archival move. No original PDF/private contacts/credentials/state/plan contents may enter evidence.

## Cost assumptions

The target below USD 1/month assumes a small low-traffic static site; it is not a guarantee. Count S3 website/state storage/requests and retained versions, CloudFront traffic/requests/invalidation and any budget charges/tax. Do not assume account credits or free-tier eligibility. Keep SSE-S3, default CloudFront hostname, bounded noncurrent history and limited invalidations; no EC2, NAT, ALB, Route53, paid KMS keys or unnecessary persistent resources. The USD 5 account-wide monthly budget notifies a private operator input at actual spend of USD 1, 3 and 5; other account usage can trigger it and spending is not capped. Preserve the official pricing references/verification date in deployment documentation and recheck prices, allowances and recipient delivery before live authorization.

## Sequence and ownership

1. Orchestrator inventories source, active references, generated artifacts and every proposed cleanup path, with reason, retained facts/evidence and canonical destination. Planner maintains specification/governance and this plan. Preserve existing work and separate ownership; do not write concurrently to the same file.
2. Builder updates Linux-first tooling and dependency checks without changing approved architecture, versions/locks or security/cost controls. Reviewer independently inspects proposed changes and all 15 scanner exceptions, rather than accepting aggregate scanner success.
3. Consolidate documentation into README.md, docs/ARCHITECTURE.md, docs/DEPLOYMENT.md, docs/SECURITY.md, docs/SDD_WORKFLOW.md, docs/VERIFICATION.md and docs/decisions/001-linux-first-terraform.md. Keep essential machine evidence under docs/evidence. Retain exact verified source/CI run identities and statuses, failed-run distinctions, individual exception dispositions, finding closures, Linux hash provenance and concise Windows OUT OF SCOPE history. Minimize duplication without losing evidence or falsifying historical commands.
4. Independent reviewer approves the complete inventory and verified consolidation before any deletion or archival move. Approval is path-specific; unresolved entries stay. Orchestrator executes only approved cleanup and verifies every retained reference/evidence path. Do not commit local caches, raw diagnostics or generated sensitive payloads.
5. Independently inspect final source and run applicable safe checks. Obtain separate push authorization where required before private publication; verify the intended remote remains private and push only the audited concrete result. Following an authorized push, run full credential-free Ubuntu CI on the exact final revision: recursive fmt; both roots init with `-backend=false -input=false -lockfile=readonly`, then validate; TFLint; Checkov and real negatives; actionlint; secret/provenance/security tests; browser/accessibility and local smoke tests. Lockfiles must remain unchanged by CI.
6. Reviewer independently inspects actual run identity/results and source changes; remediate confirmed findings and repeat affected checks. Orchestrator records sanitized command/exit/run evidence and updates verdicts. Previous green CI is historical evidence only until the changed revision passes. No queued/failed/incomplete run can pass; no missing live check is implied by source tests.

## Verdicts and stop conditions

Native Windows Terraform: **OUT OF SCOPE**, not repaired or required for release. Ubuntu implementation verification can be GO only when the full mandatory suite passes on the reviewed final revision, exceptions are justified and no confirmed source finding remains. Private GitHub verification additionally requires a verified private intended repository, reviewed sanitized source, applicable explicit push authority and successful matching-revision credential-free CI. Before that run exists, distinguish safe local preparation from implementation verification.

Public publication remains NO-GO without separate explicit authorization and privacy/content/security prerequisites. Live AWS release remains NO-GO until separately authorized and all original live checks pass: GitHub protection availability, OIDC allow/deny and least privilege, state locks/recovery, origin privacy, HTTPS/headers/metadata, deployment, drift, rollback, budget delivery and authorized temporary teardown. No readiness verdict authorizes an action. Stop at missing authorization or mandatory evidence, record NOT RUN/FAIL honestly and retain human final authority.
