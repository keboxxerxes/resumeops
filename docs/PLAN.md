# ResumeOps implementation plan

Status: specification-preserving local implementation plan. The user authorized the complete local SDD cycle; this document does not authorize AWS access, resource creation, IAM changes, publishing, push/merge, or destruction. Only the operator can authorize those actions. Read alongside `SPEC.md` and `requirements/RESUME_CONTENT.md`.

## Architecture and conservative decisions

- Build a small static `site/` using semantic HTML, local CSS and vanilla JavaScript. Use the supplied resume baseline faithfully, including skills described as in progress. Local creation is permitted; publication remains blocked. No PDF, personal email/phone, analytics, external fonts, backend, container or AI runtime. Use honest local-preview metadata until CI generates deployment SHA/time. Omit unknown repository/deployment links.
- Use `infra/bootstrap` for state storage, GitHub OIDC roles and an account-wide AWS Budget; `infra/site` for the production website; `infra/modules/website` for reusable S3/CloudFront resources. Bootstrap uses operator-controlled local state initially, then documented migration to a separate remote key. Site root can never destroy bootstrap resources.
- Use one persistent environment, production. Give its remote state a fixed explicit key. A temporary environment requires separate authorization, prefix, backend key and teardown verification; do not add a persistent development stack.
- Use S3 SSE-S3, versioning, public-access blocks and bucket ownership controls; deny insecure transport. Use CloudFront OAC with distribution-scoped S3 policy, HTTPS redirects, default root document, security response headers and default CloudFront hostname. No custom domain or paid KMS key. Bound noncurrent object retention; preserve current production content unless explicitly destroyed.
- Pin a supported Terraform version and AWS provider version and commit lockfiles for both roots. Use native S3 lockfiles. Separate state-key read/write/lock permissions; lock deletion is allowed only for the precise lock object. Runtime roles have no IAM administration, STS role-chaining, bootstrap writes or state-bucket administration.
- Bootstrap exact-repository OIDC trust with `aud=sts.amazonaws.com` and exact environment subjects: `production-plan`, `production-apply`, `production-content`, and `production-drift` as needed. A read-only plan role may trust the two exact plan/drift subjects; infrastructure apply and content deploy have distinct roles. Environments must restrict deployment to trusted `main`; required reviewers and no self-approval must be verified where approvals are required. Fail closed if the account plan or API cannot prove required protection. Operator supplies repository identity, private budget address and account-specific configuration outside committed files.
- Use PR CI without AWS credentials. Credentialed execution accepts trusted reviewed main only, never fork code or `pull_request_target`. Default automatic deployment is disabled until operator configuration and explicit authorization. All operations affecting production share a single repository-wide concurrency group with cancellation disabled, including content, apply, drift and destroy.
- Infrastructure deployment generates a fresh plan, publishes only the binary plan cryptographic digest; substantive changes are reviewed privately, and requires protected approval before applying that exact binary plan. If jobs need an artifact handoff, use authenticated encryption with an operator-configured protected-environment secret before upload, keep the key separate and plaintext out of artifacts/logs, cap retention and enforce digest, source SHA and freshness checks before decryption/application. Document how the authorized reviewer retrieves and decrypts that candidate privately, inspects the substantive plan and confirms the binary digest before approving the apply environment; a digest alone is not a plan review. Never treat approval before plan generation as review of an unseen plan. Fail closed if the protected approval/secure handoff cannot be implemented.
- Deploy only an allowlist of site assets from trusted main; generate metadata from the deployed content revision, set content types/cache headers, invalidate only changed mutable entry points and smoke-test HTTPS plus metadata. Rollback redeploys an operator-approved previous reachable revision using trusted deployment tooling. Do not execute arbitrary scripts from a historical content revision.
- Destroy is manual, production-scoped, typed-confirmation checked, protected by human approval, and serialized. Bootstrap/state are retained. Document the separate later authorization needed to remove bootstrap or retained versions.

## Threat model

| Threat / boundary | Control and residual constraint |
| --- | --- |
| Malicious PR or dependency obtains AWS credentials | Credential-free PR CI; trusted-main source check; protected environments and API verification; exact OIDC subjects/audience; SHA-pinned actions; upstream provenance checks. Human review remains required before trusted code changes. |
| Workflow injection or privileged historical revision | Pass expressions through validated environment variables; quote shell arguments; allowlist revisions/assets; checkout immutable reviewed commits; use trusted tooling for rollback. |
| Role escalation or state exfiltration | Separate roles, narrow resources/actions, no runtime IAM administration, no bootstrap permissions, exact backend keys, encrypted private state and lock. Document unavoidable AWS list/create wildcards and conditions. |
| Public origin, insecure transport or cached active content | OAC-only S3 access, public blocks, HTTPS policy/redirect, restrictive security headers/CSP, no remote scripts or trackers. Public content is intentionally readable through CloudFront only after publication approval. |
| Plan leakage/tampering or approval bypass | No plaintext artifacts/logs, authenticated encrypted handoff only if necessary, private substantive plan review, digest/SHA/freshness checks and protected apply approval after review; fail closed on unavailable protections. Terraform plan/state are sensitive even with redacted variables. |
| Competing deployments, drift/destruction or lost state | Shared concurrency, native state lock, read-only drift, typed protected site destroy, versioned separate state, documented recovery and teardown ordering. GitHub concurrency is repository-scoped; operator must coordinate local sessions. |
| Exposure of personal contact data or costs | Approved content baseline only, ignore private inputs/PDF/state/plans, scan before publication, private budget email, bounded versions/invalidation. Budgets notify; they cannot cap spend or guarantee email delivery. |
